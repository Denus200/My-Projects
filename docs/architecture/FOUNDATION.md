# Foundation v0.1 Architecture

Overlord is a modular monolith. Presentation depends on Application DTOs and commands; Application owns use-case and transaction boundaries; Domain owns entities and rules; Infrastructure implements SQLite ports.

```text
Flet Presentation → Application → Domain
                         ↑
                  SQLite Infrastructure
```

Connections are created per command/query, enable foreign keys and a bounded busy timeout, and close through context managers. Commands use one explicit Unit of Work; repositories never commit. Queries return immutable read models rather than SQLite rows.

The Dashboard is a composed query, never an entity. Task scheduling is canonical on Task: start date/time, optional end date/time, and optional deadline. Its Yesterday, Today, and Tomorrow working lists show scheduled Planned and In Progress Tasks without open Blockers, plus Completed Tasks with their existing completed treatment. Blocked and Paused Tasks keep their schedules and remain available to Tasks/Kanban, but are excluded from those actionable Dashboard lists. Dashboard owns no slots or planning assignments. The Task-owned `task_day_positions` table stores only an optional per-day presentation order; it never determines day membership. Legacy append-only `task_plans` records are preserved as history but are outside current runtime behavior. A Task may have zero to four Projects through `task_project_links`; each link may independently reference one Stage owned by that Project. The nullable `tasks.project_id` column remains only as a first-link compatibility shadow for older code and databases. Blocked state is derived from an open Blocker; Paused is a persisted lifecycle state. Cycle relationships use junction tables so Projects and Tasks remain independent across cycles.

Dashboard Weather is a separate read-only integration and owns no business data. `WeatherService` exposes an immediate normalized snapshot from an in-memory/database-adjacent JSON cache, while `OpenMeteoWeatherProvider` performs the fixed Merefa request behind the Application provider port. WMO codes are normalized into condition keys and the four approved visual families before Presentation sees them. The mounted app refreshes in a worker thread at startup and after the 30-minute freshness interval; route rendering, resize, and Sidebar changes only read the snapshot and never issue HTTP requests. Failed, timed-out, or malformed responses preserve the last successful cache, or return a contained unavailable model when no cache exists. This narrowly approved outbound Weather request does not change SQLite, Task, Project, or Cycle ownership.

Project browsing uses focused immutable read models. Infrastructure maps Project color/favorite state, linked Task counts, Project-scoped estimated time, open Blockers, current Milestone, active Project Plan and Stages, and active-Cycle context; Application exposes summaries, detail, and workspace queries; Presentation never invents database context. Eligible Project progress excludes cancelled and archived Tasks, and is unavailable when the denominator is empty. Project Plans are separate from global 12-week Cycles. One active Project Plan may own ordered Stages; Stage ownership is guarded in Domain, Application, and SQLite. Project notes are Markdown files and imported attachments are copied into the database-adjacent local `project-workspaces` directory; SQLite stores only Project-scoped metadata and safe relative paths.

Cycle browsing uses a consolidated read model for lifecycle, explicit Weekly Outcome counts, connected Projects, and next Milestone. The five-step Cycle wizard remains transient until one atomic Application command creates the Cycle graph inside a single Unit of Work. Cycle progress counts persisted Weekly Outcomes only; elapsed time is presented separately as active-week context.

Presentation keeps one mounted App Shell and replaces only route content. Its persistent Sidebar uses the packaged Overlord SVG mark, a 232-pixel expanded state, a 56-pixel compact state, and route-specific Lucide controls without changing navigation ownership. Settings is a compact categorized surface with Appearance, Planning, and Startup sections; narrow desktop widths replace the category rail with a selector. System, Light, and Dark themes resolve through centralized semantic tokens, and reduced motion suppresses nonessential motion without removing state feedback. Stable visible copy is resolved through complete English and Russian catalogs. The Sidebar language switch updates the mounted interface immediately, while migration `0007_interface_locale` persists the device locale as `en` or `ru`. Business rules remain independent from translated labels; Presentation localizes enum labels, dates, and user-facing validation errors at the UI boundary.

Shared Presentation components cover established cross-screen patterns such as page/section headings, task rows, dialog footers, empty/loading states, and non-blocking success feedback. Route and mutation errors remain contained, expose neutral user copy, and retain technical detail in local logs. Interface icons come exclusively from the pinned Lucide adapter.

Presentation validation uses `FieldValidationError(ValueError)` metadata for stable field/code routing while preserving existing user-facing messages and `ValueError` compatibility. Public pure Task form codecs live in `overlord/ui/components/task_form_values.py`. Create Task, Task Details, and Complete Task share the nullable hours/minutes control and established Task form infrastructure. All Task origins use the same Task Details modal and the same Complete Task modal rather than separate Dashboard, workspace, or Project variants.

The light-theme design foundation extends the same Presentation layer rather than creating a parallel system. Semantic tokens remain in `overlord/ui/design_system/tokens.py`; state-aware Flet styles and theme composition live beside them; reusable button, input, select, checkbox, choice-chip, and table constructors live in `overlord/ui/components/controls.py`. Active form controls use these constructors. Button, selection, form, checkbox, switch, chip, and table states share one token model, and effective reduced motion sets transition duration to zero without removing visual feedback.

Migration `0008_date_driven_tasks` introduces the canonical schedule fields and copies the current legacy planned date without deleting plan history. Migration `0009_task_day_ordering` adds persistent per-day Task presentation positions without changing Task scheduling. Migration `0010_projects_foundation` adds Project color/favorite state, Project Plans and Stages, normalized Task-to-Project links, and Project note/file metadata. It copies every legacy non-null `tasks.project_id` relationship into link position one without deleting the legacy column. Migration `0011_create_task_flow` adds an explicit normal/draft creation mode and nested Task Checklist items. Migration `0012_task_details_flow` extends the canonical lifecycle with Paused while preserving Task-owned and Task-linked rows. Migration `0013_complete_task_flow` adds nullable positive Total Time and Active Time minute values; Estimated Time remains the existing nullable total-minute field. Draft is creation intent rather than a lifecycle status and is excluded from normal Task, Dashboard, and Project execution reads until explicitly requested. The Daily Planning route/service and Primary/Secondary capacity model are retired. Tasks now presents one planning workspace with derived Kanban, week, and month modes. Contextual creation supplies either no date, today, or the selected calendar date to the same state-driven Create Task form. Project and Cycle membership remain Task relationships. Recurring actions remain outside Tasks.

The Tasks Presentation boundary has one `TaskWorkspaceState` owner in `AppSessionState`, pure projections/order transformations in `task_workspace_model.py`, service and mutation orchestration in `task_workspace_controller.py`, and a stable Flet facade in `task_workspace.py`. My Tasks/Kanban projects the canonical placement model into four visible columns: Planned, In Progress, Needs Attention, and Completed. Needs Attention groups missed/archive placement with Paused Tasks and Tasks that have open Blockers; it is non-assignable and introduces no lifecycle or storage state. My Tasks/Week projects persisted Task dates into one seven-day horizontal board with fixed-width day columns and independent list scrolling. My Tasks/Month projects the same persisted dates into a real Monday-first calendar matrix containing the necessary adjacent-month dates; responsive equal-width cells keep a fixed usable height while their shared compact Task lists scroll independently. Week/Month date-navigation expansion is transient session Presentation state that resets on view changes; it is not stored. Dashboard and Tasks share one Presentation-level per-day order transformation/controller, which delegates to the existing `reorder_for_day` Application command. Dashboard remains a read model and no scheduling or persistence format moved into Presentation.

Route refresh and asynchronous navigation share one route-render pipeline in `overlord/ui/app.py`: route preparation canonicalizes and applies route selection, one resolver builds or contains route content, and one commit updates the existing shell content, Sidebar selection, loading state, banners, timing, and logs. Asynchronous navigation adds only generation checks, thread dispatch, and delayed-loading scheduling; synchronous refresh invokes the same preparation, resolver, and commit directly. A superseded result cannot reach commit, so the mounted shell and latest route remain authoritative.

The stable and only supported product startup is the desktop command `python main.py`; `python main.py --demo` uses the isolated deterministic demo database. Web mode is retired and its former `--web`/`--port` entry points are rejected before Flet or SQLite startup. `overlord/bootstrap.py` is the composition root. A future widget may reuse Application queries through a separate read-only connection, but no widget process is part of v0.1. Foundation ends after UX Phase U5; any broader product or visual changes require a separate manual product and UX/UI redesign pass.

The earlier Presentation boundary refactor changed no persistence boundary. The later Projects foundation intentionally adds migration `0010_projects_foundation` and the local Project workspace described above. Create Task adds migration `0011_create_task_flow` so draft intent and Checklist rows participate in the same Unit of Work as the Task and its Project/Stage links. Task Details adds `0012_task_details_flow`; its save command updates Task fields, lifecycle, Project/Stage links, and Checklist rows inside one Unit of Work while preserving existing Checklist IDs. Complete Task adds `0013_complete_task_flow`; confirmation saves nullable estimate/total/active minutes and lifecycle completion in one Unit of Work while cancel and close save nothing. Explicit Task deletion disconnects the historical Cycle relation that intentionally uses `RESTRICT`, then relies on declared cascades for Task-owned data without deleting Projects, Stages, or Cycles. None of these changes modifies the production database path or desktop-only runtime.
