# Риски и технический долг

Классификация следует критериям из задания. Каждый пункт содержит конкретное основание, последствие и минимальный безопасный способ исправления; изменения в рамках аудита не выполнялись.

## Critical

**Подтверждённых Critical-дефектов в текущем состоянии не найдено.** Приложение запускается, рабочая БД проходит integrity/FK check, а хеш БД не изменился после диагностического запуска. Основание: D2/D4 в [CURRENT_STATE.md](CURRENT_STATE.md#диагностика).

Это не означает готовность к безопасному расширению: отсутствие миграций и error boundary отнесено к High, потому что текущая схема цела и текущий запуск успешен; потеря данных пока не воспроизведена.

## High

### H1. Окружение и сборка невоспроизводимы

- **Файл/участок:** пустой [`requirements.txt`](../../requirements.txt); отсутствуют `pyproject.toml`, lock-файл и build config; Flet импортируется в [`main.py`](../../main.py), строка 1.
- **Почему важно для Overlord:** запуск сегодня зависит от локальной `.venv` с Python 3.14.3 и Flet 0.84.0. На чистой машине из содержимого проекта нельзя узнать или восстановить зависимости.
- **Если не исправить:** новый компьютер, CI или сборщик не сможет гарантированно запустить приложение; обновление Flet может превратить текущее deprecation warning в ошибку.
- **Минимальный безопасный способ:** зафиксировать прямые зависимости и поддерживаемую версию Python в одном manifest + lock, документировать единственную команду запуска и затем добавить минимальный проверяемый build config. Перед фиксацией отделить прямые зависимости от транзитивных из D1.

### H2. Нет версии схемы и миграций для существующей SQLite

- **Файл/участок:** [`storage/database.py`](../../storage/database.py), строки 17–47; D2 показывает `PRAGMA user_version=0`.
- **Почему важно:** почти все планируемые модули требуют новых таблиц, связей и полей. `CREATE TABLE IF NOT EXISTS` создаёт новую БД, но не обновляет уже существующий `data/overlord.db`.
- **Если не исправить:** инсталляции получат разные схемы; новый код будет обращаться к отсутствующим столбцам/таблицам. Ручное изменение единственного пользовательского файла повышает риск потери данных.
- **Минимальный безопасный способ:** сначала зафиксировать baseline текущей DDL как migration 1, добавить backup + schema version + последовательный runner и тест миграции на копии текущей БД; лишь затем добавлять сущности.

### H3. Создание Project и Task не атомарно

- **Файл/участок:** [`ui/views/home.py`](../../ui/views/home.py), строки 152–163; отдельные `commit` в [`storage/repositories/project_repository.py`](../../storage/repositories/project_repository.py), строка 29, и [`storage/repositories/task_repository.py`](../../storage/repositories/task_repository.py), строка 49.
- **Почему важно:** сценарий выглядит для пользователя как одна операция «создать проект и сегодняшнюю задачу», но Project сохраняется до валидации/вставки Task.
- **Если не исправить:** пустой/невалидный Task или DB error оставляет неожиданный Project; повтор может создать дубликаты, потому что уникальности title нет.
- **Минимальный безопасный способ:** валидировать все поля до первой записи и выполнить compound use case в одной транзакции на уровне application unit-of-work; добавить rollback-тест.

### H4. UI сохраняет задачи, которые затем скрывает

- **Файл/участок:** [`services/today_service.py`](../../services/today_service.py), строки 13–14; [`storage/repositories/task_repository.py`](../../storage/repositories/task_repository.py), строки 67–79; add не проверяет текущий count в [`ui/views/home.py`](../../ui/views/home.py), строки 152–173.
- **Почему важно:** интерфейс обещает фокус 1–3, но не запрещает четвёртую задачу. Запись commits успешно, после refresh показываются три старейшие задачи, а новая исчезает.
- **Если не исправить:** пользователь воспринимает это как потерю данных и не может открыть скрытую задачу, потому что другого списка/экрана нет.
- **Минимальный безопасный способ:** выбрать и закрепить один контракт: либо запретить создание >3 с явным сообщением до INSERT, либо показывать все задачи и отдельно отмечать focus 1–3. Добавить UI/service regression test для четвёртой задачи.

### H5. Текущий UI практически блокирует создание второго проекта

- **Файл/участок:** dropdown автоматически выбирает первый проект в [`ui/views/home.py`](../../ui/views/home.py), строки 42–49; новый Project создаётся только если `project_dropdown.value` пуст, строки 152–158.
- **Почему важно:** при наличии хотя бы одного активного Project поле `New project` отображается, но его значение игнорируется в пользу dropdown. В проверенном окне уже был выбран существующий проект (D4).
- **Если не исправить:** Projects как самостоятельная функция не развиваются; пользователь случайно относит задачу к старому проекту или не может создать новый очевидным путём.
- **Минимальный безопасный способ:** разделить сценарии «выбрать существующий» и «создать новый», сделать взаимоисключающее состояние и покрыть кейс существующего проекта тестом.

### H6. Ошибки SQLite/старта не имеют безопасной границы

- **Файл/участок:** незащищённые connect/init в [`main.py`](../../main.py), строки 13–19; UI ловит только `ValueError` в [`ui/views/home.py`](../../ui/views/home.py), строки 103–110 и 152–173.
- **Почему важно:** Overlord хранит всё в одном локальном файле. Lock, отсутствие прав, повреждение схемы или I/O error либо сорвут запуск, либо оборвут callback без понятного recovery path.
- **Если не исправить:** пользователь увидит закрытие/зависшее действие и не узнает, сохранены ли данные; диагностика будет зависеть от консоли, которой в desktop build может не быть.
- **Минимальный безопасный способ:** добавить верхнеуровневый error boundary с read-only recovery/сообщением и логом, классифицировать ожидаемые DB errors и не повторять write автоматически. Не скрывать ошибки пустым `except`.

## Medium

### M1. Экран смешивает layout, состояние и прикладные сценарии

- **Файл/участок:** весь [`ui/views/home.py`](../../ui/views/home.py), 225 строк.
- **Почему важно:** добавление weekly progress, sessions и dashboard потребует менять один closure-heavy файл, где refresh пересоздаёт карточки и хранит control references.
- **Последствие:** высокая связанность и хрупкие UI-изменения; прикладные сценарии трудно тестировать без Flet.
- **Минимальный способ:** сначала вынести use cases/view model для load/add/update, сохранив сервисы и текущий экран; затем делить визуальные компоненты по ответственности.

### M2. Domain-инварианты частично находятся только в UI

- **Файл/участок:** positive minutes проверяется в [`ui/views/home.py`](../../ui/views/home.py), строки 51–61, но [`services/today_service.py`](../../services/today_service.py), строки 16–36, принимает любое `planned_minutes`; schema не имеет `CHECK` в [`storage/database.py`](../../storage/database.py), строки 29–41.
- **Почему важно:** будущий widget, importer или другой экран сможет записать ноль/отрицательное время. Project status и Task status также являются свободным TEXT на уровне БД.
- **Последствие:** разные entry points создадут несовместимые данные.
- **Минимальный способ:** перенести инварианты в application/domain layer и затем закрепить совместимыми DB constraints через миграции.

### M3. Модель Task привязана к сегодняшнему экрану, а не к полному жизненному циклу

- **Файл/участок:** [`core/models.py`](../../core/models.py), строки 14–26; единственная выборка списка — `list_for_date(..., limit=3)` в [`storage/repositories/task_repository.py`](../../storage/repositories/task_repository.py), строки 67–79.
- **Почему важно:** уже сохранённые прошлые задачи недоступны в UI; milestone/cycle/session/priority/order/completion semantics отсутствуют.
- **Последствие:** Weekly Progress и Cycles будут вынуждены обходить или ломать Today-specific API.
- **Минимальный способ:** не заменять Task сразу; сначала определить стабильные task use cases и добавить независимые query methods/read models поверх текущей таблицы через миграции.

### M4. Статусы не моделируют переходы

- **Файл/участок:** [`core/statuses.py`](../../core/statuses.py), строки 4–18; [`services/today_service.py`](../../services/today_service.py), строки 38–41.
- **Почему важно:** сервис принимает любой статус из enum из любого предыдущего статуса; `MOVED` и `BLOCKED` не хранят target/blocker details.
- **Последствие:** weekly metrics и audit trail будут неоднозначны.
- **Минимальный способ:** описать допустимые переходы и данные событий до добавления отчётов; не менять сохранённые значения без migration mapping.

### M5. Единственное SQLite-соединение не подготовлено к фоновым consumers

- **Файл/участок:** одно соединение создаётся в [`main.py`](../../main.py), строки 14–19, через дефолтный [`sqlite3.connect`](../../storage/database.py), строки 8–14, и передаётся всем repositories.
- **Почему важно:** desktop widget, timer work sessions или background jobs потребуют явной модели владения connections и транзакциями.
- **Последствие:** thread-affinity/locking errors либо неявное совместное использование транзакций.
- **Минимальный способ:** до фоновых модулей определить connection factory/unit-of-work «одно действие — одно соединение/транзакция» и протестировать конкурентный доступ.

### M6. Нет управляемого lifecycle соединения

- **Файл/участок:** connection создаётся в [`main.py`](../../main.py), строка 14, но close отсутствует.
- **Почему важно:** rebuild/navigation и будущие дополнительные окна могут накапливать соединения или удерживать файл.
- **Последствие:** блокировки при backup/migration/выходе.
- **Минимальный способ:** привязать close к session/window shutdown и протестировать повторные start/stop.

### M7. Тесты доказывают узкий happy path, но почти не проверяют UI и миграции

- **Файл/участок:** [`tests/test_daily_focus_services.py`](../../tests/test_daily_focus_services.py), 7 тестов; [`tests/test_startup_ui.py`](../../tests/test_startup_ui.py), строки 6–17, проверяет только отсутствие `FilePicker` в AST.
- **Почему важно:** нет теста второго проекта, >3 tasks поведения на UI, compound rollback, DB failures, navigation, validation service-level, schema upgrade.
- **Последствие:** перечисленные регрессии не будут пойманы до ручного запуска.
- **Минимальный способ:** добавить characterization tests существующего поведения и DB migration tests до рефакторинга; затем 1–2 UI smoke tests на ключевые flows.

### M8. File tools — недостижимый и незавершённый прототип

- **Файл/участок:** [`ui/views/file_manager.py`](../../ui/views/file_manager.py), строки 5–130; disabled sidebar в [`ui/components/sidebar.py`](../../ui/components/sidebar.py), строки 21–25.
- **Почему важно:** код визуально похож на готовый модуль с опасными create/rename/delete вкладками, но execute не имеет callback, preview не перечисляет реальные операции, одни и те же controls помещены в несколько Tab views.
- **Последствие:** случайное подключение создаст ложное ощущение безопасности файловых операций.
- **Минимальный способ:** считать модуль prototype-only; перед подключением заново определить безопасный preview/execute contract и отдельные controls, с тестами на пути и подтверждение destructive действий.

### M9. Нет logging/observability

- **Файл/участок:** отсутствуют logging imports/config; error feedback локален в [`ui/views/home.py`](../../ui/views/home.py), строки 38–40.
- **Почему важно:** desktop-проблемы с единственной БД иначе невозможно восстановить по фактам.
- **Последствие:** предупреждения и сбои теряются после закрытия консоли.
- **Минимальный способ:** добавить небольшой rotating local log без пользовательских текстов/секретов по умолчанию и задокументировать путь.

## Low

### L1. Частичная система стилей и дублирование визуальных значений

- **Файлы:** [`ui/style/theme.py`](../../ui/style/theme.py), [`ui/views/home.py`](../../ui/views/home.py), [`ui/views/file_manager.py`](../../ui/views/file_manager.py), [`ui/components/sidebar.py`](../../ui/components/sidebar.py).
- **Последствие:** изменение темы и Bento layout потребует правок во многих местах.
- **Минимальный способ:** расширить существующий `AppStyle` semantic tokens, не переписывая UI одним шагом. Детали: [STYLES_AUDIT.md](STYLES_AUDIT.md).

### L2. Смешение языков интерфейса

- **Файлы:** English Today в [`ui/views/home.py`](../../ui/views/home.py) и Ukrainian File tools в [`ui/views/file_manager.py`](../../ui/views/file_manager.py).
- **Последствие:** после подключения новых экранов продукт будет непоследователен.
- **Минимальный способ:** выбрать базовую locale и вынести строки перед подключением второго экрана.

### L3. Локальное окружение и bytecode загрязняют дерево

- **Файлы:** `.venv/` (7 880 файлов), множественные `__pycache__/`; `.gitignore` и Git отсутствуют. Основание: [PROJECT_TREE.md](PROJECT_TREE.md#генерируемые-и-локальные-файлы).
- **Последствие:** шум, большой backup/diff, риск принять локальные артефакты за исходные.
- **Минимальный способ:** после инициализации version control исключить env/cache/db backups; не удалять существующие файлы до согласованного backup.

### L4. `AppStyle.TEXT_SIZE` не используется

- **Файл/участок:** [`ui/style/theme.py`](../../ui/style/theme.py), строка 13; поиск ссылок на `TEXT_SIZE` не дал потребителей.
- **Последствие:** ложный token и расхождение ожиданий.
- **Минимальный способ:** либо применить как semantic body size, либо удалить в отдельном чистящем изменении после визуальных тестов.

### L5. Deprecated startup API

- **Файл/участок:** [`main.py`](../../main.py), строка 50; stderr D4.
- **Последствие:** warning сейчас; потенциальная несовместимость при будущем обновлении Flet.
- **Минимальный способ:** после фиксации версии Flet заменить на поддерживаемый `ft.run(main)` и повторить startup/UI smoke test.

## Главный архитектурный риск

Главный риск — **изменение единственной постоянной SQLite-схемы без versioned migrations и rollback/backup contract**. Все крупные планы (Cycles, Sessions, Reviews, Settings, unified Task relations) сходятся в эту точку; UI-рефакторинг можно откатить, а ошибочно преобразованные пользовательские данные — нет. Основание: [`storage/database.py`](../../storage/database.py), строки 17–47; D2 `user_version=0`; roadmap readiness в [DEVELOPMENT_OPTIONS.md](DEVELOPMENT_OPTIONS.md#готовность-к-запрошенному-развитию).
